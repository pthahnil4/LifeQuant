## 0. 术语全称（首次出现给全，后文直接用）

| 简称 | 全称 / 含义 |
|---|---|
| 幽灵合约（ghost instrument） | 本地账本里留有持仓记录、但交易所在该环境下已不存在此 `instId` 的合约。本次事故里是 `NAER-USDT-SWAP`（`NEAR-USDT-SWAP` 的误拼） |

| TTL | Time To Live，挂单存续上限（`order_ttl_periods`），超龄主动撤销，防持久挂单在交易所侧永久存续 |

## 1. 事故一句话

配置里把 `NEAR-USDT-SWAP` 误写成 `NAER-USDT-SWAP`。这个币种在 OKX 实盘不存在（回 `code=51001`），
但它已在本地 V2 账本留下一行 `sync_error` 记录；此后每一轮轮初对账都必然在它身上失败，
对账闸门因此永久关闭，**四个正常交易币种（XRP/SOL/LTC/ETH）的开仓额度全部被归零**，
同时每轮白白多花 100~200 秒去同步 6 个"已经没有事实可核对"的账本残留。

## 2. 完整因果链（一条链解释"被拦"和"变慢"两个症状）

```
config 里 instId 误配 NAER-USDT-SWAP
   └→ OKX get_instruments / 下单查询回 51001 "Instrument ID ... doesn't exist"
      └→ 该币种从配置删掉也没用：账本 kv_store 里那行还在
         └→ 轮初对账范围 = 配置 ∪ 本地账本 ∪ 交易所目录，NAER 仍在并集里
            └→ 五步稳定性快照永远取不到合约规格 → synchronize 失败
               ├→ failed_sync 非空 → _account_sync_ok=False → 【对账闸门关闭】全账户禁增仓
               └→ 残留 sync_error 留在内存账本 → _entry_room() 遍历"其它合约"时命中
                     if state.get('sync_error') ... : return 0.0
                  → 即使闸门放行，其它币种的额度也逐个被归零（max_total_position>0 时生效）
         └→ 另 6 个已移除币种（ARB/BICO/LIT/NEAR/PENGU/TRUMP）的空账本同样进入并集
            └→ 每个白跑一轮五步快照（实测 20s+/币）→ 整轮从 5.5~9.8s（2 币）涨到 93~224s
```

### 顺带纠正一个调度语义（曾被我误判）

`execution_interval_seconds` 是**两轮开始之间的最小间隔**，不是"一轮的时间预算"：
`start_real_scheduler` 在阻塞执行之前就写 `last_execution['batch']=current_time`，
所以一轮实际耗时超过 cd 时，间隔形同虚设 —— 这就是"cd 40s 却 224s 一轮"的原因，
也是"以前 8 个币能在 cd 80s 内连收 8 封邮件"成立的原因（当时每币只要 3~5s）。

## 3. 修复 B：运行时豁免（代码，已落地）

### 3.1 `instrument_spec.py`：把"合约不存在"与"临时失败"分开

- 新增 `_is_not_exist_response(r)`：只认 `code=51001` 或 msg 含 `doesn't exist`。
  **限频(50011)/超时/空响应/非 dict 一律不算否定** —— 否则一次网络抖动就能让真实持仓脱离对账。
- 新增内存态 `self._not_exist`（不落库）；`_fetch_remote` 成功时撤销判定。
- 新增 `instrument_exists(inst_id) -> Optional[bool]`：True 存在 / False 明确不存在 / **None 未知**。
  三态是这次修复的安全支点：**未知不等于不存在**。该方法不得作为能否下单的依据。

### 3.2 `trend_range_trader.py`：轮初对账范围划分 `_partition_sync_scope`

把并集里的每个合约判成"本轮必须同步"或"无事实可核对（跳过）"，口径如下（**顺序即优先级**）：

1. 在当前配置里，或出现在交易所持仓/未成交挂单目录里 → **无条件同步**；
2. 账本记着真实敞口（`held>0`、非终态槽位、`unknown/cancel_requested/qfail` 标记、
   兜底委托 algo 在位、`exchange_totals>0`、未终结的市价平仓意图）→ **同步**；
   此时即使交易所已无此合约，也只打【账本待核实】错误日志、绝不静默放行；
3. 账本干净且无风险标记 → **跳过**（并且不联网问存在性，不白打接口）；
4. 仅带风险标记（`settlement_pending/external_order_watch/external_open_orders/algo_unknown/sync_error`
   或未消化的人工 `pause_until`）+ 交易所**明确**无此合约 → **跳过**并从内存账本丢弃该条目；
5. 存在性未知（查询失败/异常/规格缓存不可用）→ 保守照旧同步。

跳过的条目只做一件事：`self.pos_mgr.state.pop(inst, None)`（**仅内存，不删库**），
目的是让它们退出 `_entry_room()` 的总额度遍历，不再把正常币种的额度归零。
跳过清单按集合签名去重打印，并指向本文件的 A 方案做彻底清除。

新增的辅助判定：`_ledger_open_interest()`、`_ledger_risk_flags()`、`_slot_unsettled()`、
`_spec_instrument_exists()`（用 `getattr` 防御 `__new__` 构造的裸实例桩）。

### 3.3 一条重要的口径修正：终态残留不算敞口

实盘账本体检发现"受保护"的 5 个已移除币种（ARB/BICO/LIT/NEAR/TRUMP）**持仓与快照都是 0、也没有风险标记**，
被判定为有敞口的唯一原因是槽位记录停在 `FILLED`/`EXPIRED` —— 那是成交入账/撤单确认之后的**终态残留**，
不是待解释事实。因此 `_ledger_open_interest` 引入 `_SLOT_SETTLED = ('IDLE','FILLED','EXPIRED')`：

- 终态 + 无 `unknown/cancel_requested/qfail_logged` → 不算敞口（可跳过）；
- 不认识的槽位状态 → 一律当在途处理（保守）；
- 市价平仓意图 `market_orders` 同口径，只算未终结的。

`_cleanup_ghost_ledger.py` 的 `has_open_interest()` 用**完全相同**的口径，
避免"体检说可删、运行时却认为有敞口"两套标准。修正后体检结果从
"9 受保护 / 1 幽灵 / 1 闲置"变成"4 受保护（都是配置内币种）/ 1 幽灵 / 6 闲置"。

## 4. 修复 A：账本清理脚本（运维，需你确认执行）

`crypto/task/_cleanup_ghost_ledger.py`（新增，268 行）：

```powershell
# 第一步：只读体检（联网问合约存在性，一个字都不改）
python -B crypto/task/_cleanup_ghost_ledger.py --account quantlimit --detail

# 第二步：停掉实盘调度器（必须），再真删
python -B crypto/task/_cleanup_ghost_ledger.py --account quantlimit --apply --scheduler-stopped
# 连 6 个闲置空账本一起清（推荐，否则它们仍留在库里，重启后又回来）
python -B crypto/task/_cleanup_ghost_ledger.py --account quantlimit --apply --scheduler-stopped --include-idle
```

三条硬约束：

1. **默认只读**：不带 `--apply` 只打印分类报告。
2. **永不删除有事实的条目**：在配置里、或有真实敞口/风险标记的一律 `PROTECTED`；
   合约存在性查询失败也归入 `PROTECTED`（未知不等于不存在）。
3. **必须显式声明调度器已停**：只给 `--apply` 不给 `--scheduler-stopped` 直接退出码 2。
   原因：V2 账本用 `_revision` 乐观锁（fail-stop，不自动恢复），进程在跑时改库会让它
   下一轮写入撞版本冲突并被**永久 latch**，表现就是"对账闸门关闭"再也不会开仓 —— 反而更糟。

脚本还会打印目标库（密码掩码）与删除后剩余条目数；`--account legacy` 用于清换代前的
`PosBook/PosSlot/PosAlgo/PosLev` 四张拆表。注意它与根目录 `_cleanup_ledger.py`（清分析缺档台账）不是同一个东西。

## 5. 为什么没有按最初要求"移除对账闸门"

你当时要的是"别拦着我把任务跑完"，但闸门本身不是病灶：它报的"NAER 未完成对账"是真话，
错的是那个合约根本不存在。删掉闸门等于把"账实不符时也照下单"变成常态 —— 一旦真的出现
漏成交、外部改仓、撤单未确认，就会在不知情的情况下重复开仓或漏平仓，这是资金安全网，
不能为了赶一轮任务拆掉。本次的处理是：**闸门保留，但让它只对"真有事实要核对"的合约说话**，
幽灵与空账本不再有权关闭全账户。

## 9. 仓位量精确核对与补足（大白话版）

> 本章是配套设计文档《交易对账与闸门机制最终设计方案.md》的落地口径确认，
> 不引入任何新的全局阻断逻辑。关联代码：`position_order_manager.py` 的
> `reconcile()` / `_entry_room()` / `_exit_room()` / `_place_entry()` / `_place_exit()`。

### 9.1 为什么不能「看到有仓就不动」

**「有仓」不是结论，「差多少」才是结论。** 检测到已有仓位只是量了一下体温，
真正的判断必须是一道减法：

| 你的操作 | 配置目标 | 实际已开 | 正确反应 | 错误反应 |
|---|---|---|---|---|
| 提前开了一点 | 5 张 | 2 张 | **补开 3 张** | ❌「已经有仓了」→ 什么都不做 |
| 提前开够了 | 5 张 | 5 张 | 跳过开仓，照常挂止盈/平仓单 | ❌ 再开 5 张变 10 张 |
| 提前开超了 | 5 张 | 7 张 | 不减、不干预，等信号翻转统一清 | ❌ 立刻砍掉 2 张（跟人工抢方向盘） |

系统从来不是「开关」，而是**补足器**：实际下单量 = `max(0, 目标额度 − 已占用)`。
「跳过」只是这道减法算出 0 时的**结果**，不能当成跳过对账、随便放行的**借口**。

### 9.2 这笔账具体怎么算（现成机制，逐条对应代码）

```
方向总额度  =  趋势仓(A)目标量 + 区间仓(B)目标量      ← set_entry_targets
已占用      =  max(交易所真实持仓, A账本 + B账本)      ← 关键：取 max
             + 各篮子在途未成交的开仓单剩余量
本次补开    =  方向总额度 − 已占用                     ← 再向下取整到 lotSz
                                                    不足 minSz 记为 0（不可下单）
```

两条不能动的硬口径：

1. **占用取 `max(交易所, 账本)`** —— 你在交易所手动开的仓，哪怕还没被本地账本吸收，
   也一定被算进「已占用」。所以「人工提前开 + 系统再开一遍」这条路是**关死**的，
   防重复开仓靠的是这个 max，不靠闸门。
2. **本币种的在途挂单也算占用** —— 上一轮的 opening 单还挂着没成交，这一轮不会又补一张，
   避免「持仓 + 挂单」合计超额（这是历史上真实出过的事故）。

### 9.3 A / B 两篮子怎么隔离：各记各的账、各平各的仓

先讲清一个容易误会的事实：**交易所那边只有一份净头寸，没有「A 的」和「B 的」之分**。
「哪几张属于趋势仓、哪几张属于区间仓」完全是本地账本的记账归属
（`BUCKET_TREND` / `BUCKET_RANGE` 各自独立的 `held / avg_px / slots`）。
所以「B 平仓不会把 A 一起平掉」靠的是下面三层，缺一层都不成立：

| 层 | 机制 | 效果 |
|---|---|---|
| ① 记账隔离 | 两篮子各自 `held`，谁开的记在谁名下，成交回报按 `bucket` 入账 | B 的止盈单只按 B 的量算 |
| ② 软件封顶 | `_exit_room` = 真实同向持仓 − **其它篮子已挂的平仓量** | 两篮子不会重复平同一批仓 |
| ③ 交易所硬约束 | 平仓单是 `reduce-only` | 物理上不可能把仓位翻成反向 |

举例：A 持 0.5 张、B 持 0.3 张，B 触发止盈该平 0.3：
→ 只挂 0.3 张 reduce-only 平多单，成交后账户从 0.8 降到 0.5，**A 的 0.5 张一张不少**。

唯一「两篮子一起清」的时点是**长周期信号反转 / 夜间风控强平 / 人工强平**——
那时按策略本意要清空该方向全部持仓（包括吸收进来的人工仓），是设计，不是误伤。

诚实说明两条边界（不粉饰）：

- 人工直接在交易所**部分平仓**时，`reconcile` 只会看到「总仓位少了」，
  于是按各篮子原持仓**等比例摊减**（日志 `【对账·shrink】`）。
  如果你想只平 B，账本可能把少量缩减摊到 A 头上 —— **归属会有轻微失真，但总量绝不虚增**，
  不会因此多开也不会漏平。
- 人工**凭空开仓**（两篮子原本都是 0）被吸收时，会记到趋势仓名下
  （除非区间仓的 `last_desired` 方向刚好一致）。这意味着这笔仓由 A 的平仓逻辑管，
  B 的止盈不会去动它 —— 恰好符合「别误伤另一个篮子」的诉求。

### 9.4 各种「提前动手」的处理一览

| 你做了什么 | 对账看到什么 | 系统下一步动作 |
|---|---|---|
| 提前开仓、不够 | `【对账·absorb】` 占用 < 目标 | 开仓窗口内**补开差额**，不撤你已开的仓 |
| 提前开仓、刚好 | 占用 = 目标 | 减法算出 0 → 跳过开仓（带【开仓跳过】原因日志），止盈/风控照常挂 |
| 提前开仓、超了 | 占用 > 目标 | 不减仓、不干预；等信号翻转的平仓窗口统一清同方向全部 |
| 提前平掉一部分 | `【对账·shrink】` + 触发人工冷却 | **本轮不补仓**，进入 `pause_until`（配置项 `manual_close_pause_minutes`）；冷却到期后按额度自动补回差额 |
| 全部平掉 | 真实持仓 = 0，账本归零 | 该币多余的平仓单自动撤销（无仓可平）；开仓按窗口重新判断是否补足 |
| 开了反向仓 | 净持仓模式判定不支持该方向 | **只隔离这一个币**并告警（设计方案 G1），其它币种照常交易 |

**关于「提前平仓后要等冷却才补」这一条**：这不是僵化，是防止「你刚手动平掉，
系统下一轮立刻又买回去」跟你抢方向盘。冷却时长可在配置里调（含设为 0）。
冷却只锁**该币的开仓**，永远不锁平仓、撤单，也不牵连其它币种 —— 与
《交易对账与闸门机制最终设计方案.md》的「局部隔离」完全一致。

### 9.5 状态感知与闸门的分工（两者相乘才下单）

```
该做多少  ←  状态感知（算账）：目标 − 占用 = 补足量 / 该平量
能不能做  ←  闸门分级（G1 只锁该币 / G2 账户形状未知 / G3 持久化失效）
实际下单  =  两者相乘；任一为 0 都不下单，但都不许「连坐」
```

明确三条不引入新阻断的边界：

1. 闸门分级**最小到币种**，不存在「A 篮子有分歧就锁住 B 篮子」这种篮子级连坐，
   更不存在「废弃币种账本残留锁住全账户」（本次事故病灶）。
2. 状态感知（算账补足）**永远默认开启**，它不需要「先通过五步快照才允许工作」——
   快照的职责是确认「这个币的事实问清了」，而不是给正常流程设卡。
3. 本章所有口径都是**对既有代码行为的确认**（`_entry_room` / `_exit_room` /
   `reconcile` 现状即如此），实现阶段要做的只有下面这一条可见性增强。
