# 定时任务系统全模块说明（事无巨细版）

> 本文把 `crypto/task/` 下"定时任务系统"的**每一个功能模块**、以及它背后的
> **交易账本 / 版本冲突 / G0~G3 闸门 / 单实例租约**机制，从头到尾讲清楚。
> 目标：任何人（包括未来的我）读完这一篇，就能知道系统里到底跑了哪些定时任务、
> 每个任务干什么、交易是怎么一轮一轮跑的、账本为什么必须存在、"版本冲突"和
> "G3 停摆"到底是怎么触发的、以及当前还遗留哪些坑。
>
> 文中所有结论均来自对源码的直接核对，涉及行号以撰写时代码为准。
> 标注 ✅=已在代码中确证；⚠️=已发现的隐患/待修；🔎=需线上日志进一步确认的推断。

---

## 0. 一句话总览

- **调度中枢**：`scheduler.py` 里的 `TaskScheduler`（基于 APScheduler 的后台调度器），
  全项目单例 `task_scheduler`。所有定时任务都在它身上注册。
- **交易本体**：`trading_scheduler` 这个任务不是 APScheduler 的定时 job，而是一个
  **常驻线程**，跑 `TrendRangeTrader.start_real_scheduler()`，按固定间隔一轮一轮地
  "分析→对账→止盈止损→挂单"。
- **账本**：交易所（OKX）只返回**一份净持仓**，不区分"这是趋势仓还是区间仓、
  这是系统开的还是人工开的"。这套归属信息**只存在于本地账本**里。账本一旦写坏或
  写不进，系统就无法安全下单——这就是 G3 停摆的由来。
- **反复瘫痪的真凶**：账本用 `_revision` 乐观锁防并发写；一旦检测到"别人也写了这一行"
  就抛"版本冲突"，触发 G3 全局停单。冲突来源既可能是**第二个进程**，也可能是
  **同一进程内的并发写**（本次事故属于后者的可能性大，见第 5 章）。

## 2. 调度中枢 `scheduler.py`（TaskScheduler）

### 2.1 APScheduler 配置 ✅
`TaskScheduler.__init__` 建一个 `BackgroundScheduler`，job 默认：
- `coalesce=True`：错过的多次执行合并成一次（不补跑堆积）。
- `max_instances=1`：**同一 job 最多 1 个实例在跑**——上一轮没结束，本轮不会重入。
- `misfire_grace_time=60`：错过触发点 60 秒内仍补执行，超过则丢弃。

单例：模块底部 `task_scheduler = TaskScheduler()`，全项目共用。

### 2.2 任务注册与"统一开关"双层治理 ✅
所有注册都走 `register_job(func, trigger, job_id, job_name, ...)`。它内置一道
**统一开关守卫**：`job_id` 不在 `_NON_SWITCHABLE_JOBS` 里时，先查开关，关着的任务
直接被拦下不入队。开关有两个来源，任一关即关：

1. **kv_store `task_switches`**（`/task` 页面每个任务的持久开关，即点即生效，重启不丢）。
2. **`config.json` 顶层 `task_switches` 块**（免登录的文件级一键急停，带 mtime 缓存，
   改文件不用重启）。**文件级只能单向关**：文件写 `false` → 一律关；文件 `true`/缺省 →
   听 kv 与默认值。

判定入口 `task_switch(name, default=True)`；读失败一律 fail-open（当"未关"），
**开关存储坏了绝不能连带把实盘关了**。

`_NON_SWITCHABLE_JOBS = ('trading_scheduler',)`：交易调度器不参与页面开关（它自带
启停按钮与自愈开关）。`SWITCHABLE_JOB_LABELS` 存"job_id→中文名"，保证任务被关掉后
列表里仍有占位行，用户能再打开。

### 2.3 全部定时任务清单 ✅（`register_default_jobs`）

| job_id | 名称 | 触发 | 干什么 | 是否碰交易/账本 |
|---|---|---|---|---|
| `trading_scheduler` | 实盘交易调度器 | **常驻线程**（手动启动） | `TrendRangeTrader.start_real_scheduler` 主循环 | **是（核心）** |
| `alert_monitor` | 监控告警（行情异动/持仓盈亏） | interval（kv 配置周期） | `alert_monitor.run_alert_check` | 只读行情/持仓，发信 |
| `analysis_discipline` | 分析纪律 | interval | 小时槽合格判定 + 缺口提醒 + 每日日报 + 网页倒计时 | 只读，发信；关时自行 remove_job |
| `daily_memory_reset` | 每日内存主动归零重启 | cron 默认 04:03 | 低波动窗口主动重启清内存；三条件拒绝执行 | 触发重启（间接影响交易） |
| `instinct_shadow_predict` | 盘感影子预测 | 整点·串行 | LLM 影子预测，**仅记录不交易** | 否（只写 instinct_* 表） |
| `instinct_settle` | 盘感满窗结算 | 10 分钟 | 影子预测满窗结算 | 否 |
| `batch_trend_auto` | 批量趋势自动分析 | 每 4 小时 + 晨间 | `batch_schedule` 批量多周期趋势分析，晨间链式推强币邮件 | 只读行情，写分析结果；**不写账本** |
| `checkin_reminder` | 打卡倒计时提醒 | 每 5 分钟巡检 | 距上次打卡满 N 分钟未续打则邮件提醒 | 只读计划树，零写库 |
| `checkin_diary_reminder` | 每日评级收尾提醒 | cron 23:30 | 当天缺评级/缺日记则发收尾提醒 | 只读，零写库、不碰 OKX |

> 注册顺序即 `register_default_jobs()` 里的顺序；每个注册都包 `try/except`，
> **单个任务注册失败不影响其它任务**（日志 warning 后继续）。

### 2.4 交易调度器集成（线程型）✅
- `start_trading_scheduler(account, source)`：`new TrendRangeTrader(...)` → 起一个
  `daemon=True`、名为 `TradingScheduler` 的线程跑 `start_real_scheduler`。
- **启停竞态护**（`_trading_lock`，RLock）：`stop` 只置标志、不等线程退出（一轮可能
  跑几十秒到几分钟）；`start` 侧做"上一轮线程仍存活则拒绝"，避免"旧线程还在按旧账本
  下单 + 新线程又起" → 重复开仓。
- `stop_trading_scheduler`：**走 `trader.stop()`**（除置停外还释放跨进程租约，否则租约
  要等 TTL 才过期，期间无法立即重启）。等线程收尾最多 `TRADING_STOP_JOIN_SECONDS`
  （默认 15s），等不完就如实返回"收尾中"。
- `force_close_position(close_type)`：Web 强平入口，委托给**同一个** `_trading_scheduler`
  的 `force_close_manual`（即同一个 pos_mgr，不新建账本写入者）。

### 2.5 重启自愈拉起 ✅（`schedule_auto_resume` / `_auto_resume_worker`）
进程启动尾声由 app.py 调用，**幂等**（已有一个存活线程就不再起）：
- 真实启动路径只传 `boot_info`（`process_lifecycle` 的归因结果：为什么重启），起不起/
  等多久/要不要先发预告信，全交给 `plan_resume` 按"夜间直接接回 / 白天留 10 分钟否决窗 /
  重启风暴熔断"决定。
- `_auto_resume_worker`：`if self._trading_running: return`（已被人工起过就不重复起）；
  睡完再读期望状态 `desired_running`——这段时间你去页面点"停止交易"会清掉它，本次拉起
  自然作废（**现成的人工否决通道**）；只有"上次希望在跑 + auto_resume 开关开"才
  `start_trading_scheduler(source='auto_resume')`。
- 归因/策略层任一不可用 → 回退"不自动拉起"这个保守值。

## 3. 实盘交易主循环（`TrendRangeTrader`）

文件：`crypto/task/trend_range_trader.py`（约 3955 行，系统最大单体）。

### 3.1 一轮批量 `run_real_trading_batch()` 的完整流水线 ✅
```
run_id = generate_run_id()
1) 续约租约 _renew_trader_lease()：被别的进程接管则 fence 自己、stop()、直接 return
2) _run_count += 1
3) with self._trade_lock:                       # 与 Web 强平互斥
   3.1 pos_mgr.set_context(run_id, False)
   3.2 pos_mgr._probe_storage_recovery()        # G3 瞬时故障每轮探活自愈（见 6.3）
   3.3 if not pos_mgr._storage_ok:              # G3 停摆短路
           _note_persist_halt(run_id); return   # 不读交易所/不逐币对账/不进主循环
   3.4 读账户事实：try_get_positions_by_mode() / try_get_open_orders()
       任一为 None → 本轮禁止交易（G2 账户形状未知）
   3.5 _partition_sync_scope(...)：把"已移除币种的账本残留/交易所无此合约"剔除，
       避免一次注定失败的快照把全账户开仓额度归零
   3.6 _sync_round_instruments(...)：逐币 synchronize 对账，得出本轮 G1 隔离集合
   3.7 主循环：逐币 analyze_and_trade_real(...)
       - _note_cycle_result：连续失败达阈值升级告警邮件
       - 统计 ok_cnt / link_fail_cnt
   3.8 _note_link_health：整批读失败达阈值 → 一封聚合链路告警
4) 本轮结束日志：══ 本轮结束 | 成功 X/Y | 耗时 Zs ══
```

> **耗时警示**：日志实测出现过**单轮 223 秒**（多币 K 线 `timed out` 串行重试拖长）。
> 这与租约 TTL 180s 冲突，见第 5、7 章的 ⚠️。

### 3.2 双仓位（两个篮子）✅
每个合约的账本分两个独立篮子：
- `BUCKET_TREND='trend'`（趋势跟踪仓）
- `BUCKET_RANGE='range'`（区间波动仓）

每篮子各有 `entry`/`exit` 两个槽位（`SLOTS`），按 `long`/`short` 两个方向分别记
`held`（持仓张数）与 `avg_px`（加权均价）。**A 仓（趋势）/B 仓（区间）各记各账、
各平各仓、互不连坐**——这是用户的硬需求，也是账本存在的核心理由。

### 3.3 各类"冷却/暂停"（都只锁开仓，不锁平仓）✅
- `pause_until`（人工强平冷却，持久化到 manual_pause/账本）：人工平掉的仓，冷却期内
  不自动开回来，跨重启保持。
- `_tp_close_until`（止盈止损冷却，内存态）：全平成功后 N 个短周期内禁自动开新仓。
- `_range_pause_until`（区间仓 B 风险退出冷却，内存态）。
- `_spike_until`（插针保护，默认关闭）：单轮环比涨跌超阈值暂停开仓几分钟。
- `_entry_blocked`（本轮人工干预闸门）。

## 4. 交易账本（重点）

文件：`crypto/trader_state_repo.py`（数据访问层）+
`crypto/task/utils/position_order_manager.py`（`DualPositionOrderManager`，账本的内存态与
读写编排）。

### 4.1 为什么必须有账本（不可删）✅
OKX 永续合约在**净持仓模式**下，一个合约只返回**一份净头寸**。它不知道：
- 这份持仓里，哪部分是"趋势仓"、哪部分是"区间仓"；
- 哪部分是"系统按策略开的"、哪部分是"你手动开的"。

**这些归属拆分只存在于本地账本。** 没有账本，系统就无法：
- 分别对 A/B 两个篮子记账、各平各仓；
- 区分"人工提前开的仓"（要吸收进账本，而不是再开一遍 → 防重复开仓）；
- 在重启后恢复"我上一轮挂了什么单、成交到哪、止盈阶梯走到第几档"。

所以"把账本撕了"= 系统失去对持仓归属的唯一记忆 = 无法安全地按策略运行。账本不可删。

### 4.2 存储结构 ✅
`save_inst_position(session, inst_id, s, account, environment)` 有**两条路径**：

**A. 有账号（`account is not None`，实盘常态）→ KVStore JSON-key：**
- key = `pos_v2:{sha256(f'{environment}:{account}')[:20]}:{instId}`（≤64 字符，按账号+环境分区）。
- value = `{'schema': 2, 'state': {...整个合约账本..., '_revision': N}}`。
- 写入走 `config_store_repo.patch_json_config(session, key, update, strict=True)`
  —— **行锁原子写 + 乐观锁校验**（见 4.3）。

**B. 无账号（`account=None`，迁移/兜底工具用）→ 4 张 SQL 表：**
`PosBook`（每篮子 held/avg_px/确认标志）、`PosSlot`（entry/exit 槽位）、
`PosAlgo`（止盈止损算法单）、`PosLev`（杠杆设置）。按 `inst_id` 整段重写（单次 ≤9 行）。

`load_position_state(session, account, environment)`：有账号读 KVStore（**带 `_revision`**，
版本号自洽）；`schema != 2` 或结构不对 → 抛"交易账本损坏，禁止按空仓启动"（绝不静默当空仓）。

### 4.3 `_revision` 乐观锁——版本冲突的确切来源 ✅
`save_inst_position` 有账号分支的核心（逐行）：
```python
expected = int(s.get('_revision', 0))          # ← 从【内存账本】读当前版本号（拿行锁之前！）

def update(current):                            # current = 行锁内从【DB】读到的最新值
    revision = int((current.get('state') or {}).get('_revision', 0))
    if revision != expected:                    # DB 版本 ≠ 内存版本 → 认为"有别人写过"
        raise RuntimeError('交易账本版本冲突：存在其他写入者，停止交易并重新恢复状态')
    state = copy.deepcopy(s); state['_revision'] = expected + 1
    return {'schema': 2, 'state': state}

patch_json_config(session, key, update, strict=True)   # 行锁内执行 update
return expected + 1                                     # 提交成功后返回新版本
```
调用方 `DualPositionOrderManager._save` 在**事务提交成功后**才把新版本写回内存：
```python
revision = state_repo.save_inst_position(...)   # 提交
if self.account is not None:
    self.state[inst]['_revision'] = revision     # 内存版本号跟进
self._saved_state[inst] = copy.deepcopy(self.state[inst])
```

**冲突判定的本质**：内存里记的版本号 `expected`，与"拿行锁那一刻 DB 里的实际版本号"
不一致，就判定"存在其他写入者"。单进程串行时二者永远相等；**只要有第二个写入者在
两次读之间动了这一行，`expected` 就变成陈旧值 → 冲突**。

## 5. 版本冲突（重点）——反复瘫痪的真凶

### 5.1 触发后的连锁反应 ✅
`_save` 抛"版本冲突" → 落进 except：
```python
self._storage_ok = False          # G3 latch
self._storage_fatal = True        # ← 版本冲突归为"致命"（本次修复新增，见 6.3）
self._storage_error = str(e)
```
→ `run_real_trading_batch` 轮首 `_storage_ok=False` 短路 → 每轮 `_note_persist_halt`
→ 日志 `══ 第N轮跳过 | 持久化不可用(G3·账本版本冲突) 全局停单，需人工排除并发写入者后重启进程恢复 ══`
→ **交易全局停摆，且致命 latch 不自动恢复，必须重启进程。**

### 5.2 谁是"第二写入者"？两类 ✅
1. **跨进程**：第二个 `app.py`/调度进程（重启时旧进程没死干净、或误开双实例）在写同一份
   `(account, environment)` 账本。→ 由**单实例租约**根治（第 7 章）。
2. **进程内并发**：同一个进程里，两个线程几乎同时对**同一个 inst** 调 `_save`。

全项目 `DualPositionOrderManager(` **只实例化一处**（`trend_range_trader.py:230`），
Web 强平也委托给同一个 trader/pos_mgr——所以**不存在第二个 manager 对象**。因此进程内
并发只可能是"同一个 pos_mgr 被两个线程同时 `_save`"。

### 5.3 本次事故复盘（18:29:15）🔎
关键事实（均来自日志）：
- 第 1 轮 `成功3/4`、`耗时223.1s`（极长，伴随多币 `K线获取失败: timed out`）。
- 冲突发生在**第 1 轮进行中**（18:29:15），紧跟着 `LIT 人工强平冷却结束，恢复自动开仓`
  与 `LIT 信号反转`。
- 之后 第 2~6 轮全部 `G3·账本版本冲突` 跳过（同一个 trader 的 `_run_count` 连续，
  说明**只有一个 trader 在跑**，没有第二个进程/实例的交错日志）。

由此推断（🔎，需线上日志最终坐实）：**这是进程内并发写，不是第二个进程。** 最可能的两条路径：

- **⚠️ 隐患 A：`_save` 未全程持 `pos_mgr._lock`。**
  `position_order_manager` 里 `get_book/close_market/synchronize/poll_fills` 等都在
  `with self._lock` 下，但 **`_save` 本身不加锁**，且 `hold_entries`（571 行 `_save`）等
  路径也不在锁内。`save_inst_position` 的 `expected` 又是在**拿 DB 行锁之前**从内存读的。
  于是：线程 A 在 `synchronize` 里持锁 `_save(LIT)`（expected=N，提交后 DB=N+1、内存=N+1）；
  与此同时线程 B 走**未持锁**的 `_save(LIT)`（早一步读到 expected=N），B 拿行锁时 DB 已是
  N+1 → `N != N+1` → **误报"存在其他写入者"**。真正的"其他写入者"其实是自己进程的另一个线程。

- **⚠️ 隐患 B：租约续约只在轮首，长轮中途租约失效。**
  租约 TTL=180s，而本轮耗时 223s > 180s，`_renew_trader_lease` 只在**每轮开头**调用一次
  → 本轮进行到第 180 秒时租约已过期。若此时自愈线程/另一进程判定"没有存活持有者"而起了
  第二个 trader，就会与仍在跑的第 1 轮并发写账本。（本次日志未见第二个 trader 的交错输出，
  故 A 的可能性更大；但 B 是确凿的设计漏洞，必须补。）

### 5.4 修复方向（尚未落地，等你点头）
1. **把 `_save` 的"读内存版本→写库→回写内存版本"整段纳入 `pos_mgr._lock`**（RLock 可重入，
   已持锁的调用方不受影响），让进程内对同一 manager 的保存彻底串行——从根上消灭隐患 A 的
   误报。
2. **租约续租改进**：在长轮内部（如每币处理前）也 `_renew_trader_lease()`，或把 TTL 提到
   远大于最坏单轮耗时（如 600s）并在每币循环里心跳续约，堵住隐患 B。
3. 二者都不改当时“版本冲突=致命停摆”的安全语义，只是**不再让自己进程误伤自己**。
   （注：该“致命停摆”即 G3，已于 2026-09-28 按用户要求移除；但上述 `_save` 加锁串行化修复**保留**。）

## 6. 闸门分级 G0~G3（⛔ 已于 2026-09-28 按用户要求彻底移除，本节仅作历史存档）

> **当前代码已无 G1/G2/G3 任何闸门判定、字段与告警邮件。**对账失败/账户形状未知/
> 持久化不可用都不再停单、不再隔离币种；交易按内存账本照常继续。具体当前行为见 6.1。
> 以下分级表为移除前的历史设计，**不再代表现状**。

设计文档（已作废）：`crypto/交易对账与闸门机制最终设计方案.md`。原核心原则：
**故障域与风险范围严格一致；闸门只拦"新增风险"（开仓/加仓），永不拦"削减风险"
（平仓、撤单、止盈止损、人工干预通道）。**

| 级别（已移除） | 名称 | 原触发条件 | 原影响面 | 原恢复方式 |
|---|---|---|---|---|
| **G0** | 正常 | 对账通过 | 无限制 | — |
| **G1** | 币种隔离 | **单个币**自己的事实没问清（该币对账 unresolved） | **只锁该币加仓**；平仓/撤单与其它币照常 | 下一轮该币对账通过即自动解除 |
| **G2** | 账户形状未知 | 持仓/挂单**目录查询失败**（`try_get_positions_by_mode`/`try_get_open_orders` 返回 None），或总仓位被未确认敞口击穿 | **全账户禁新开仓**；平仓/撤单放行 | 目录查询恢复即解除 |
| **G3** | 持久化不可用 | 写不进账本（`_storage_ok=False`） | **全局停单**（连平仓都不发，因为发了记不进账本=幂等失效） | 见 6.3 分致命/瞬时 |

### 6.1 G1/G2/G3 闸门已按用户要求彻底移除（2026-09-28）⛔
历史事故（2026-09-27 NAER 幽灵合约、以及 2026-09-28 单进程反复“账本版本冲突”）曾促成
 G1（币种隔离）/G2（账户形状未知）/G3（持久化不可用）三道闸门。但闸门在实盘中反复
误伤正常交易（一报“币种级停开仓”就把交易瘫痪、预警刷屏），用户明确要求彻底移除。

**当前行为（闸门已不存在）**：
- 对账失败、账户形状未知（如 long_short_mode）、账本落库失败（含版本冲突）都
  **不停单、不隔离币种、不发闸门告警邮件**；`synchronize` 失败只记 `sync_error` 供诊断。
- 交易按内存账本照常继续，DB/网络恢复后下一次 `_save` 自动补写未落库的增量。
- **防重复开仓**不再依赖闸门，而由 `_entry_room` 的 `max(交易所真实持仓, 账本合计)`
  算已占用 + `max_position`/`max_total` 单币与总仓硬上限保证；人工强平/手动平仓冷却
  （`_entry_blocked` + `pause_until`）仍只锁本币开仓。
- **幽灵合约**（交易所已无此 instId）仍走 `absent` 零阻断权 + `_maybe_auto_watch` 自动降级观察。
- **跨进程双写**（两个调度进程同写一份账本→版本冲突）不再靠 G3 停摆兑现，而由
  **单实例租约**（启动抢占/每轮续约/第二个进程检测到存活持有者即拒启）从根上杜绝。

> 已删除的闸门专属冒烟：`_smoke_soft_gate.py`（G0~G3 分级）、`_smoke_save_race.py`（G3 竞态 latch）。
> `_save` 整段纳入 `self._lock` 的串行化修复**保留**（它消除同进程假版本冲突，与闸门无关）。

## 7. 跨进程单实例租约守护 ✅

文件：`trader_state_repo.py` 末尾租约段 + `trend_range_trader.py` 接线。

- **key**：`trader_lease:{sha256(f'{environment}:{account}')[:20]}`；**TTL=180s**（`LEASE_DEFAULT_TTL`）。
- **holder_id**：`make_lease_holder_id()` = `主机名:pid:随机8位`（每个 trader 实例唯一）。
- **acquire**（`__init__`）：抢占租约；检测到**其他存活持有者**（未过 TTL）→ 抛
  `LeaseRefusedError` → `start_trading_scheduler` 捕获 → 页面提示"已有调度在运行"，**拒绝启动**。
- **renew**（每轮开头）：续约；若已被别人接管 → **fence 自己**（`stop()`）并停轮，杜绝双写。
- **release**（`stop()` / `start_real_scheduler` 末尾）：释放，避免等 TTL 才能重启。
- **fail-open**：租约取得/续约**异常**（DB 抖动等）一律放行，**绝不因租约本身把交易锁死**。
- 崩溃自动过期接管：持有者进程崩了不再续约，TTL 到点后新进程可接管。

**⚠️ 已知漏洞（见 5.3 隐患 B）**：续约只在轮首，单轮 > TTL（如 223s > 180s）时租约会
中途失效。**待修**：长轮内部心跳续约，或 TTL 提到远大于最坏单轮耗时。
