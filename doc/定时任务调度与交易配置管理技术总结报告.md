# 定时任务调度与交易配置管理技术总结报告

编制日期：2026-09-22  
核对范围：当前工作区源码，包含尚未提交的修改；不是线上运行状态审计。  
阅读对象：希望理解系统机制、设计取舍及后续建设方向，而不必逐行阅读源码的项目负责人。

## 一、结论先行

当前系统可以概括为：**Flask 提供管理入口，APScheduler 负责后台周期任务，独立线程负责实盘交易，数据库保存配置与运行意愿，本地文件承担兼容和降级作用。**

需要先明确六件事：

1. **“后台调度器运行”不等于“实盘交易运行”。** 两者在同一 Python 进程中，但采用不同执行链路。任务页面把它们放在一起展示，不代表共用一个启停开关。
2. **“定时任务全局开关”不是全系统停机按钮。** 它控制已纳入名单的后台定时任务，不停止实盘线程，也不停止独立的内存看门狗和系统监控线程。
3. **交易配置以数据库为主。** 正常读取顺序是账号专属配置、旧全局配置、本地文件；文件并不是与数据库平等、实时互相复制的第二主库。
4. **多账号隔离已经实现，但尚未贯穿全部路径。** 数据库专属键能够隔离配置，旧全局兜底和共享文件仍可能破坏这一边界；一个调度器实例同一时间只管理一个实盘账号。
5. **保存配置不等于立即完成交易动作。** 核心策略参数由交易循环重新读取，在后续轮次消费；保存不会自动启动交易，不意味着仓位立即达到新目标，也不是“全字段原子热切换”。
6. **已具备多道防竞态措施，但不是分布式调度平台。** 同任务防重入、交易启停锁、交易操作锁、策略引擎锁都已存在；这些主要是进程内保护，多进程、多服务器仍需要额外设计。

本报告将“当前确实实现的行为”“从代码可推导的风险”“建议新增的能力”分别说明，不把设计目标写成已经保证的事实。

## 二、系统现状与职责划分

### 2.1 架构关系图

```text
浏览器 /task（task.html）
       │ HTTP：加载、保存、状态查询、启停
       ▼
Flask 管理接口（crypto/app.py）
       ├── 配置仓储（config_store_repo.py）
       │       └── MySQL kv_store：配置、任务开关、运行意愿
       │
       └── task_scheduler：进程内单例管理器
               ├── APScheduler：监控、纪律、归零、盘感、批量分析
               ├── TradingScheduler 线程：单账号实盘交易循环
               └── TradingAutoResume 线程：重启后的一次延时恢复尝试

交易循环（trend_range_trader.py）
       ├── 读取该账号交易配置
       ├── 同步交易所持仓与挂单事实
       ├── 策略分析 → 趋势仓 / 区间仓决策
       └── 交易执行器 + 账号/环境隔离账本

同进程旁路线程：memory_watchdog、system_monitor
外部进程管理器：在 Python 进程退出后重新启动进程
```

这里的“独立线程”只表示控制流分离，**不是进程隔离**。Web、计算、监控仍共享进程内存、部分锁及外部 API 配额；进程退出时这些线程一起结束。[S1][S2][S7]

### 2.2 当前任务清单

下表列出源码中的默认注册项和触发规则。实际是否注册，仍取决于配置、环境变量、依赖导入是否成功，不能仅凭表格断言线上正在执行。

| 类型 / 任务 ID | 职责 | 触发机制与默认值 | 主要条件 |
|---|---|---|---|
| `trading_scheduler` | 实盘分析、持仓对账、双仓位交易 | 独立循环线程；执行间隔默认 60 秒 | 手动启动，或符合条件的重启自愈；不属于普通 APScheduler 任务 |
| `alert_monitor` | 行情异动、持仓盈亏、风险及交易循环存活告警 | interval；默认 300 秒，配置下限 30 秒 | 统一任务开关 + 告警业务配置 `enabled` |
| `analysis_discipline` | 分析纪律巡检、小时槽判定、缺口与日报提醒 | interval；当前固定 300 秒 | 统一任务开关 + 纪律业务配置；邮件另有独立开关 |
| `daily_memory_reset` | 在满足条件时主动退出进程，以释放累计内存 | cron；默认每日 04:03 | 统一开关、`CRYPTO_DAILY_RESET`、内存水位、策略是否忙、恢复条件 |
| `instinct_shadow_predict` | 盘感影子预测，只记录、不实盘交易 | cron；每小时整点 | 统一开关、`CRYPTO_INSTINCT_AUTO`、LLM 已配置 |
| `instinct_settle` | 对已满观察窗口的影子预测做结果结算 | interval；每 10 分钟 | 与影子预测注册入口共用环境和 LLM 条件，另受自身任务开关约束 |
| `batch_trend_auto` | 批量趋势分析，晨间轮次结束后发送强币摘要 | cron；默认 00:05、04:05、08:05、12:05、16:05、20:05 | 统一开关 + `batch_schedule_config`；邮件可单独关闭 |

补充说明：

- 调度封装支持 interval、cron、date 三种触发器，但当前上述默认注册项没有使用 date；实盘重启延时使用的是线程等待，不是 date 任务。
- `batch_trend_auto` 已接入当前工作区的默认注册入口。其“分析后发晨报”采用链式执行，避免两个独立任务无法保证先分析、后取数发信。遇到手动批次在跑时跳过本轮分析；晨间档可以限时等待该批次，然后读取已有最新数据发送摘要。
- 批量任务默认筛选 4H 与 1D 同向、ADX_4H > 25、ATR_4H > 20，按 ADX 排序取前 10。这里是行情数据自身的指标口径，不是交易配置中的仓位参数，也不是自动下单指令。
- `memory_watchdog` 默认每 2 分钟检查进程内存，`system_monitor` 默认每 60 秒检查系统健康；它们由应用直接启动，不在上述普通任务开关名单里。
- 业务上的任务计划、打卡、结算模块，与本报告的“运行后台函数的调度器”不是同一概念。

依据：[S1][S2][S8][S9][S10][S11]。

### 2.3 多层开关到底控制什么

普通后台任务在注册时，基本遵循：

```text
允许注册 = 数据库全局开关
         且 数据库该任务开关
         且 文件全局开关
         且 文件该任务开关
         且 该任务自身条件满足
```

数据库保存于 `kv_store` 的 `task_switches`，结构是“全局 enabled + jobs 内各任务开关”；文件控制位于 `crypto/config.json` 顶层的 `task_switches`，任务开关直接放在该块内。二者不是相同结构，也不是彼此同步的镜像。

| 控制入口 | 实际作用 | 不应作出的理解 |
|---|---|---|
| 页面“启动 / 停止调度器” | 调用 APScheduler 的 start / shutdown | 不启动或停止实盘交易线程；也不是持久开关 |
| 页面“定时任务全局开关” | 持久化任务总闸；关闭时移除名单内后台任务 | 不覆盖整个应用，也不撤单或平仓 |
| 页面单任务开关 | 保存该任务意愿；关闭移除，打开重新注册默认任务 | 移除不等于强制中断已经执行的任务体 |
| 文件 `task_switches` | 对注册条件追加单向禁止；文件 false 压过页面 true | 不是所有任务都具备“修改文件后立即中断”的能力 |
| 交易配置 `global_settings.enabled` | 控制该账号是否进入币种策略处理 | 不退出线程，不自动清空交易所持仓 |
| `risk_control.emergency_stop` | 让配置读取返回空策略处理列表 | 不是账户级全撤单、全平仓按钮 |
| 币种 `trade_enabled=false` | 进入观察模式，保留分析与提醒 | 不代表没有任何转换动作：进入时有撤销篮子挂单的逻辑 |
| “停止交易” | 发出交易线程停止信号并限时等待退出 | 不等于持仓已平、挂单已撤 |
| `auto_resume` | 允许符合条件的重启后自动恢复 | 不等于现在启动，也不取代普通启停 |
| `CRYPTO_NO_BACKGROUND` | 在应用导入时抑制预热和后台启动 | 不是在线动态开关，也不是禁止全部 API 的安全沙箱 |

两个容易误解的细节：

1. **策略禁用后仍有账户事实同步。** 当前交易批次会先同步持仓与挂单，即使币种列表为空也会做同步，再跳过策略决策。因此不能说“禁用后完全不访问交易所”。但这也不等于原先所有主动止盈、止损管理仍继续执行。
2. **文件开关可被重新读取，不等于任务自动取消。** 文件内容按修改时间缓存，下次判定能读到新值；多数任务只在注册阶段检查统一开关，已入队任务并没有统一的执行前校验包装。文件开关的限制详见风险章节。

普通任务开关读取失败按“未关闭”处理，即 fail-open，意图是不因一次配置故障关闭全部提醒。交易重启恢复则设计为 fail-safe：无法确认时不自动下单。两种故障取向服务于不同目的，不应混用。[S2][S3][S7]

分析纪律还有业务联动：模块总闸同时用于打卡闸门、网页提醒等路径；如果只是嫌邮件多，应使用纪律配置里的 `email.enabled`，而不是关闭整个纪律任务。已经在途的任务不保证立即终止。[S9]

## 三、调度器如何融入主应用

### 3.1 启动过程

根目录 `app.py` 导入 `crypto.app` 的 Flask 应用。应用注册路由、Web 访问闸门后，按后台开关决定是否进行下列动作：

1. 启动数据库异步预热。
2. 创建 `scheduler-boot` 守护线程。
3. 在线程内调用 `register_default_jobs()`，让各模块登记自己的任务。
4. 启动 APScheduler。
5. 归因本次进程启动的原因，再安排一次实盘自动恢复尝试。
6. 另外启动内存看门狗和系统监控线程。

这样做的目的，是把数据库初始化、监控依赖加载等慢操作移出 Web 的同步导入路径，缩短页面服务启动等待。相应代价是：**页面已经能访问时，调度器可能还没准备好。** 状态接口对此做了容错，例如任务尚未真正入队时允许没有 `next_run_time`。[S1][S2]

`register_default_jobs()` 对各模块分别捕获注册异常：一个监控模块失败不会阻止其他模块启动。这是故障隔离的取舍，但也意味着“调度器启动成功”并不能证明“全部任务注册成功”，仍需核对任务清单和日志。

### 3.2 普通任务的执行保护

APScheduler 的统一默认设置为：

- `max_instances=1`：同一任务不同时运行两份。
- `coalesce=True`：可合并的错过执行合并处理，避免恢复后集中补跑。
- `misfire_grace_time=60`：允许一定的迟到窗口，而非无限补发。
- 同名注册默认 `replace_existing=True`：避免在同一调度器内重复登记同名任务。

这些保护的边界是“当前进程里的当前任务”。不同任务仍可能争抢相同资源；其他进程里的同名任务不会被这套实例计数拦住。

当前没有配置数据库 JobStore。任务定义与注册元信息主要存在内存中，进程重启后靠默认注册入口重建；数据库持久化的是开关和业务配置，而不是完整执行队列。因此不具备天然的“宕机期间每次触发都补回来”或“恰好执行一次”保证。[S2]

### 3.3 实盘交易为何另用循环线程

实盘需要把“账户对账、信号计算、风控、两类仓位处理”组织成连续、有顺序的执行过程。当前由 `TrendRangeTrader` 自己掌管循环，管理器只负责实例的启停和状态展示。

执行过程可以理解为：

```text
启动时建立交易账号上下文与账本
    ↓
循环读取执行间隔和部分热配置
    ↓
距离上次批次开始已达到间隔？
    ├── 否：等待后继续检查
    └── 是：读取币种配置 → 账户事实同步 → 逐币种串行处理
                         → 再次对账 → 风控 → 趋势仓 → 区间仓
```

主循环正常检查等待为 10 秒，异常后等待 30 秒。间隔按批次开始时间比较，而不是按 K 线整点触发。若一轮分析耗时超过设定间隔，下一轮只能等上一轮结束后再检查，不会补出多个并发批次。

因此，“间隔 60 秒”表示调度检查条件，**不是严格每分钟完成一轮，更不是每 60 秒必定下单一次**。币种增多、行情读取变慢、策略锁等待都会影响实际轮次间隔。[S7]

### 3.4 启停竞态与重启恢复

当前已有三类关键互斥：

| 保护 | 解决的问题 | 边界 |
|---|---|---|
| 管理器 `_trading_lock` | 串行化实盘启停，旧线程仍活着时拒绝再启动 | 只保护当前进程 |
| Trader `_trade_lock` | 单币处理与人工强平互斥，避免对账和交易操作被横插 | 不等于整个配置更新事务锁 |
| `PRO3_LOCK` | 防止策略引擎模块级参数被不同调用链并发改写 | 正确性得到保护，但计算吞吐受到串行约束 |

停止交易时先设置 `running=False` 和停止事件，再在锁外限时等待，默认 15 秒；没退出就显示“收尾中”。启动端还检查旧线程是否存活，避免停止请求返回后又创建第二个 trader。状态接口同时提供“运行标志、线程存活、是否收尾”，比单一绿色状态灯更准确。[S2][S7][S12]

重启恢复使用独立的 `trading_runtime` 数据：`desired_running` 表示用户希望运行，`account` 表示账号，`auto_resume` 表示是否允许自动恢复，另记录最近事件与时间。它不是线程运行状态的实时副本。

恢复策略的设计规则包括：

- 初次上线：不自动交易。
- 每日计划内归零：默认等待 20 秒后恢复，成功时静默。
- 内存重启、异常死亡、冷启动：默认夜间 00:00—08:00 等待 20 秒；白天预告后等待 600 秒。
- 默认 6 小时内自愈类重启达到 3 次，触发熔断。
- 识别出同机并发实例时，不自动恢复交易。
- 最终还需 `desired_running` 与 `auto_resume` 均为真。

这些是当前策略函数的规则，**不表示所有异常分支都已严格遵守目标**。归因缺失、等待期间停止和状态写入失败仍存在需要补强的路径，见 6.6。[S2][S6][S13]

## 四、交易配置如何管理与同步

### 4.1 配置的三个层次

| 层次 | 管什么 | 存放方式 |
|---|---|---|
| 交易账号接入配置 | 账号标识、名称、交易所环境及访问凭据 | `api_config.py`，通过 `get_api_config(account)` 获取 |
| 策略配置 | 币种、周期、杠杆、双仓位参数、全局策略控制 | `kv_store` 的账号专属 JSON，另写本地镜像 |
| 交易运行状态 | 用户是否希望运行、上次账号、是否允许自动恢复 | `kv_store` 的 `trading_runtime` |

账号下拉接口只返回 key、名称和默认标记，不返回访问凭据。**选择账号，就是选择执行身份与配置命名空间，不是把密钥传到浏览器。** 本报告不包含任何凭据值。[S6][S14]

### 4.2 数据库作为主存

`kv_store` 是通用键值表，主要字段为：

- `key`：唯一键，当前模型长度为 64。
- `value`：JSON 文本，存一整份配置。
- `updated_at`：更新时间。

例如，两个示意账号 A、B 分别使用：

```text
strategy_config:A → A 的币种、杠杆和双仓位配置
strategy_config:B → B 的币种、杠杆和双仓位配置
strategy_config   → 旧全局配置，兼容回退使用
```

策略字段经常演化，用 JSON 整份存取可以减少表结构迁移，并与原 JSON 文件保持接近，适合当前规模。代价是：数据库不能直接保证每个策略字段都正确，也没有天然的字段级合并和版本冲突检测。

`updated_at` 目前不是保存接口使用的乐观锁版本号；非关键配置的 TTL 缓存使用进程内单调时钟计时，不是每次拿该字段向数据库核对。[S4]

### 4.3 读取路径与账号解析

Web 接口带 `?account=...` 时按指定账号读取。不带时，`_resolve_task_account()` 优先取当前交易管理器持有的账号，否则使用 `DEFAULT_ACCOUNT`。

之后遵循：

```text
账号专属 strategy_config:{account}
    ↓ 无可用结果
旧全局 strategy_config
    ↓ 无可用结果
当前进程所在机器的 task/config/config_trend_range.json
```

Trader 在建立账号上下文后，也通过同一仓储读取该账号的策略配置。

保留全局回退的设计意图是平滑迁移：代码先上线、专属配置尚未准备好时，避免突然完全失去旧参数。但现有读取结果把“键不存在、内容不可用、数据库读取失败”等情况都可能表现为 `None`。因此，这是一条兼容性优先的回退链，**不是严格的账号隔离保证**。

还有两点边界：

- 无账号上下文的监控 / 纪律消费者可以通过 `load_live_strategy_config_cached()` 从持久化 `trading_runtime.account` 取账号；这与 Web 的“当前内存账号，否则默认账号”并不是完全相同的解析入口。
- 配置键只有账号维度，没有交易所环境维度；账本则注入了账号和环境。当前此 Trader 校验要求实盘 `flag=0`，未来扩展模拟盘时应同步设计配置命名空间。

依据：[S3][S4][S5][S7]。

### 4.4 缓存：函数名仍叫 cached，但关键配置已经不走 TTL

当前 `config_store_repo.py` 做了分级处理：

- 普通配置使用进程内 30 秒 TTL，例如 `task_switches`、批量调度业务配置。
- `strategy_config`、所有 `strategy_config:{account}`、`trading_runtime` 等关键键绕过 TTL，每次读取回源数据库。
- 写入后在事务提交阶段失效缓存；还有 generation 屏障，防止提交前发出的旧查询在提交后重新填入旧缓存。
- 返回深拷贝，避免调用者修改返回对象时污染缓存。

所以，历史注释中“交易配置最多等 30 秒生效”的说法，已不完全符合当前代码。如今关键参数是否被采用，主要取决于**交易循环何时再次读取、该业务环节如何消费参数，以及数据库是否成功提供数据**。

这一修改降低了关键配置陈旧风险，但也增加数据库访问次数；同一轮多次读取还可能混入不同版本，后续宜改成“每轮固定配置快照”。[S4][S7]

### 4.5 保存流程：双写，不是双向同步

普通保存请求按以下顺序处理：

1. 后端校验完整配置。
2. 解析账号，写该账号的专属数据库键。
3. 退出数据库会话上下文时提交事务。
4. 用同一份配置覆盖本地 `config_trend_range.json`。
5. 根据数据库写入结果、失败后的读取探测，返回成功、降级或失败。
6. 保存接口还尝试更新历史币种库。

当前返回行为应这样理解：

| 数据库写入 | 文件写入 | 接口行为 | 实际含义 |
|---|---|---|---|
| 成功 | 成功 | 成功 | 数据库为后续正常读取提供新配置；本机文件也已更新 |
| 成功 | 失败 | 异常分支返回失败 | 数据库实际上已经提交，交易端可能采用新值；不能把“接口失败”理解为完全没保存 |
| 失败 | 成功，且目标数据库键仍读得到 | 返回失败 | 文件虽新，正常读取仍可能是旧数据库参数 |
| 失败 | 成功，且探测读不到目标键 | 返回降级成功提示 | 代码推断可用文件，但这个推断并不覆盖旧全局键回退等所有情况 |
| 失败 | 失败 | 返回失败 | 本次不能保证任何新配置可用 |

**当前没有以下机制：**数据库与文件之间的跨资源事务、文件更新自动回灌数据库、数据库变更自动广播到其他机器文件、离线文件变更在数据库恢复后自动合并。

例如，本地保存 A 的配置会更新共享数据库里的 A 专属键，同时只更新本地机器的一份文件，不会把服务器上的镜像文件也更新。数据库恢复后，读取仍以库中配置为先，文件中的降级修改可能不再被采用。[S3][S4]

### 4.6 双仓位策略参数的业务含义

配置主干是“币种数组 + 全局设置”。每个币种里有公共参数和两个独立策略篮子。

| 参数分组 | 主要内容 | 不读源码时的理解方式 |
|---|---|---|
| 币种公共参数 | `instId`、短 / 长周期、杠杆、信号算法、开平仓参考价格 | 确定分析什么市场、用什么节奏和信号 |
| 人工方向 | `manual_direction=auto/long/short` | 双周期模式下主要锁定长周期方向，短周期仍保留真实信号，不是无条件立即下单 |
| 币种交易开关 | `trade_enabled` | 允许自动交易或转入观察提醒 |
| 趋势仓 A | `trend_position`：启用、single/dual、数量模式、止盈止损、交易所保护委托 | 主要跟踪趋势信号；single 为单周期双向模式，dual 为双周期单向模式 |
| 区间仓 B | `range_position`：启用、数量模式、BOLL 周期与偏差、改单最小幅度 | 主要围绕 BOLL 边界交易，并在对侧边界管理退出 |
| 全局策略设置 | 启用、执行间隔、紧急停止、持仓上限、邮件冷却、夜间处理、反向持仓守卫 | 对该账号整份配置施加约束；不是 APScheduler 的全局设置 |

两仓是**策略归属上的两个篮子**，不是两个账号，也不保证在交易所看到两份独立净持仓。同方向持仓可能合并显示，系统靠账本区分归属，并在统一对账后依次处理。项目还采用全仓多头、逐仓空头的映射，这是本项目执行约定，不是所有交易系统都如此。[S7]

两仓分别设置下单规模，支持：

- `size_mode=contracts`：直接输入张数，再按合约步长取整。
- `size_mode=usd`：字段虽然叫 `notional_usd`，当前执行含义实际是**占用保证金预算**，会乘杠杆后换算张数。

简化换算为：

```text
名义持仓价值 ≈ 保证金预算 × 杠杆
张数 = 向下取整到 lotSz（预算 × 杠杆 ÷ 每张合约当前价值）
```

规格缺失、价格不可用或不足最小下单量时，返回零规模，不强行挂单。该预算计算也不意味着消除了价格波动、手续费或滑点影响。

例如示意预算 10 USDT、杠杆 5 倍，目标名义价值约为 50 USDT，而不是 10 USDT。后续文档和界面应统一术语，避免字段旧名称造成仓位认知偏差。

止盈止损配置归属趋势仓，区间仓以自身 BOLL 边界逻辑管理。趋势仓支持固定目标、追踪、动能、通道、分批等主止盈类别及时间止盈辅助；止损支持固定或 ATR 类型。保存校验负责检查结构与部分数值约束，交易时仍需通过合约规格、实际持仓、风险控制与订单状态等检查。[S3][S7]

## 五、task.html 如何加载与保存

### 5.1 页面并不是直接编辑服务器文件

页面是 Flask 模板，交互主要由模板内 JavaScript 完成。浏览器只通过 API 读写 JSON；真正访问数据库、写本地文件、启动线程的是后端。

初始化时，页面分别请求账号列表、恢复配置和调度状态；这些请求不是一个串行事务。账号列表加载完成后，会再加载当前选择账号的交易配置。切换账号、进入交易配置标签页也会重新加载。[S15]

### 5.2 主要 API 契约

| API | 页面用途 | 后端动作 |
|---|---|---|
| `GET /api/task/trading/accounts` | 填充账号下拉框 | 返回账号 key、名称、默认标记 |
| `GET /api/task/config/trading?account=...` | 加载策略配置 | 账号专属 → 全局 → 文件 |
| `POST /api/task/config/trading?account=...` | 保存策略配置 | 完整校验后双写；不是单字段补丁 |
| `GET /api/task/status` | 刷新任务与实盘状态 | 汇总调度器、任务、开关、线程状态 |
| `POST /api/task/start`、`/api/task/stop` | 启停普通调度器 | APScheduler 生命周期操作 |
| `POST /api/task/job/<job_id>/switch` | 单任务勾选框 | 持久化开关并移除 / 重注册 |
| `POST /api/task/switches/global` | 后台任务总闸 | 持久化全局开关并移除 / 重注册 |
| `POST /api/task/trading/start` | 启动所选账号 | JSON body 携带 account，创建 trader |
| `POST /api/task/trading/stop` | 停止交易 | 停止事件 + 限时收尾等待 |
| `GET /api/task/trading/runtime` | 加载自动恢复开关 | 读取运行意愿及启动归因信息 |
| `POST /api/task/trading/runtime/auto-resume` | 保存自动恢复开关 | 更新持久化运行意愿配置 |

接口通常返回 `{code, message, data}`。这里的 `code` 是 JSON 业务字段；多处错误分支没有同步设置 HTTP 状态码，不能只用 HTTP 200 判断业务成功。

当前 `task.html` 的状态刷新入口是初始化、刷新按钮和操作后的 `refreshStatus()`；模板内没有看到定时 `setInterval` 状态轮询，不应把旧注释里的“高频轮询”当成当前页面行为。[S3][S14][S15]

### 5.3 加载、编辑、提交的完整路径

```text
选择账号 A
    ↓
GET 配置接口，URL 携带 account=A
    ↓
后端返回整份 JSON
    ↓
浏览器保存为 _tradingConfig，并把第一个币种填入表单
    ↓
用户编辑当前币种 / 全局设置
    ↓
点击保存：采集当前表单，合并到 _tradingConfig
    ↓
POST 整份 JSON，URL 再次携带当前下拉框账号
    ↓
后端校验、数据库提交、文件镜像更新
    ↓
页面根据 code 与 message 显示结果
    ↓
交易循环在后续配置读取与业务处理时采用参数
```

重要交互规则：

- “全局通用配置 / 一键应用”指的是**当前账号内跨币种复制**，不是跨账号同步。
- 公共周期、杠杆、信号与双仓位参数可批量复制；币种 ID、人工方向和自动交易开关被保留。
- 保存时尽量合并现有对象，保留未暴露在界面上的字段，但部分嵌套对象仍会被重建；不能理解为所有未知字段都绝对保留。
- 币种拖拽排序修改内存数组，保存后影响执行顺序。
- 移除币种不自动平仓。当前批次仍会对账本和真实账户目录做同步，但被移除币种不会继续走原有完整策略处理流程。
- 当前切换币种直接重填表单，未先采集原币种未保存的表单；切换账号或重新加载也可能覆盖草稿。编辑后应明确保存，后续宜增加脏数据提示。
- 运行中状态刷新会锁定账号下拉并设置为正在运行的账号，但不会由此自动重新请求该账号的配置，这也是账号绑定竞态的来源之一。

保存失败会展示后端校验错误。普通保存使用后端消息，但全局同步 / 自定义成功提示可能替换后端消息，从而遮蔽降级提醒；建议把“成功结果”和“警告信息”拆成独立字段。[S15]

## 六、潜在风险与改进建议

优先级说明：P0 为应优先补强的资金 / 账号安全边界，P1 为较高的一致性与运行可靠性风险，P2 为扩展性和可维护性改进。除 6.4 的独立库级实验外，以下均为源码路径分析，不是对线上事故的认定，也未进行实盘破坏性复现。

### 6.1 P0：多账号隔离没有贯穿降级与管理路径

**当前证据：**账号专属数据库键隔离了正常配置读写；但所有账号保存同一个本地文件，缺专属键时还会回退旧全局配置。管理器 `force_close_positions()` 枚举币种时直接读取 trader 的共享文件，没有使用账号专属仓储。[S2][S3][S4]

**可能后果：**

- A 的专属配置不可用时，可能读到全局或最后由 B 写入的文件参数。
- 批量强平入口的目标币种可能与当前账号的数据库配置或真实持仓不一致，出现漏处理或处理范围偏离预期。
- 多机器共享数据库时，各机器的本地镜像可能不同。

**建议：**

1. 为配置定义统一的账号 / 环境作用域，并验证账号存在、长度合法。
2. 本地快照也按账号 / 环境分开，文件内记录账号、版本和来源。
3. 旧全局回退只用于明确的迁移流程；实盘发现专属配置缺失时，拒绝不明确的参数继承。
4. 强平目标以该账号真实持仓与在途订单为主，并由统一服务层协调账本；不要用共享配置文件充当完整账户目录。
5. 降级时明确保留已有仓位保护，拒绝用不明来源参数新增风险，而非简单关闭所有保护能力。

### 6.2 P0：前端账号选择与配置内容可能错配

**当前证据：**配置请求没有取消旧请求或响应序号校验；`_tradingConfig` 不记录所属账号；提交时使用“当前下拉框账号”。初始化的账号加载与状态请求并行，状态刷新可以改变下拉框而不重载配置。[S15]

**场景：**先请求 A，再请求 B，若 A 的响应最后到达，就可能用 A 的内容覆盖编辑区，而下拉框仍是 B；此时保存会把内容提交到 B 专属键。即使只有一个使用者，慢网络与多个标签页也可能触发。

**建议：**将 `loadedAccount + revision + config` 绑定成编辑会话；账号切换期间禁用保存，取消旧请求或只接纳最新序号的响应；后端返回解析后的账号，并在保存时核对。状态刷新改变运行账号时，必须同时重新建立一致的编辑上下文。

### 6.3 P1：整份覆盖、共享文件和多次读配置带来一致性风险

**当前证据：**交易配置保存为整份覆盖；任务开关也是读 JSON、修改、整份写回，没有使用现有行锁合并能力。文件用普通覆盖写入，没有原子替换。交易循环及其辅助函数会多次读取关键配置。[S2][S3][S4][S7]

**可能后果：**

- 两个标签页分别修改不同字段，后保存者用旧整份内容覆盖先保存者。
- 同时切换两个任务开关可能互相覆盖。
- 并发保存的数据库提交顺序与文件写入顺序不同，最终库 / 文件内容可能不一致；读取者也可能碰到正在写入的半份 JSON。
- 同一轮使用旧币种参数、新风控参数，难以复盘当轮究竟使用了哪个配置版本。

**建议：**

- 整份配置引入 `revision`，保存携带 `expected_revision`，冲突返回 409 并提供差异。
- 小字段开关采用已存在的 `patch_json_config()` 事务内锁定合并能力。
- 镜像采用同目录临时文件加原子替换，并按版本防止旧写覆盖新写。
- 每轮获取一次不可变配置快照，把版本传递到分析、风控、订单日志；紧急停止则保留独立高优先级检查，不因固定快照延误。

### 6.4 P1：普通调度器 shutdown 后复用，可能“显示运行但不执行”

**源码路径：**页面停止调用 `_scheduler.shutdown(wait=False)`，再次启动仍复用同一 `BackgroundScheduler` 对象，没有重建已关闭的执行器。[S2][S3]

**本次验证：**在本机已安装的 APScheduler 上，用一个全新的内存调度器执行“start → shutdown → start → 提交仅设置内存事件的一次性任务”，得到：

```text
RuntimeError: cannot schedule new futures after shutdown
restarted_running= True job_executed= False
```

实验没有导入项目应用、连接数据库、发邮件或调用交易接口。它确认了当前依赖环境的生命周期风险，不等于已验证线上页面发生过同一故障。

**建议：**普通管理操作采用 pause / resume；只有进程退出才 shutdown。若必须支持完全停止后重建，应创建新调度器和执行器、重新注册允许任务，并用实际任务执行心跳确认恢复。仅检查 running 标志不足以验收。

### 6.5 P1：开关持久化与实际调度状态不是一个原子操作

**当前证据：**HTTP 先保存开关，再执行 remove / register；统一文件开关主要用于注册守卫，未对所有任务做执行前检查。打开单个任务还会重新注册全部默认任务。[S2][S3]

**可能后果：**

- 数据库显示关闭，但移除失败或任务已开始执行，仍可能继续一轮。
- 只改文件或在另一进程改开关，当前已注册任务不一定被移除。
- 重新注册无关 interval 任务可能重置其下一次执行时间，频繁切换会扰动调度节奏。
- 将来新增任务若未加入名单，全局关闭不能保证主动移除它。

**建议：**维护统一任务定义表，提供“只重建指定任务”；增加期望状态与实际状态的协调器；任务包装器在执行前检查统一开关。涉及发信、交易或进程退出的长任务，在关键副作用前增加取消检查，并区分“已禁用、已停调度、运行中待结束”。

### 6.6 P0：重启自愈的保守意图仍有异常分支缺口

源码显示三个值得优先补强的路径：[S1][S2][S6]

1. **归因结果完全缺失：**应用归因异常后会传入 `None`；`schedule_auto_resume()` 此时没有生成拒绝计划，而是把 `plan=None` 交给等待线程。若之后读到 `auto_resume=true` 且 `desired_running=true`，仍可能尝试自动启动。不能把“未知归因策略会拒绝”推广成“所有归因失败都拒绝”。
2. **等待恢复期间点击停止：**尚无交易线程时，`stop_trading_scheduler()` 可能在“未运行”分支提前返回，未清除 `desired_running`。因此预告里的“点停止即可否决”并非所有状态下都成立。
3. **状态保存失败：**运行状态仓储会吞掉部分写入异常；`set_auto_resume()` 没有把保存失败标志传到 HTTP 层，可能返回看似成功的值。人工停止时若状态落库失败，旧的期望运行记录也可能残留。

**建议：**真实启动路径缺归因时必须产生明确拒绝计划；“停止 / 取消恢复”无论当前线程是否存在，都先持久化停止意愿并撤销待执行恢复；失败必须向页面反馈。恢复前在统一状态锁下复查账号、期望状态、配置版本和唯一执行权。维护“待恢复、已取消、恢复失败”明确状态，而不是仅靠延时线程和布尔值推断。

### 6.7 P1：单进程锁无法解决多 worker、多服务器重复执行

**当前证据：**后台启动发生在应用导入阶段；任务管理器、APScheduler、交易锁都是进程内对象。启动归因虽能识别部分同机并发实例，但不是跨机器租约，也不覆盖全部人工启动路径。[S1][S2][S13]

**建议：**近期明确部署约束为单后台执行实例；需要扩展时，将 Web、普通调度、交易执行拆成明确角色。按账号 / 环境建立带续租与 fencing token 的执行所有权，防止旧实例失联后继续下单。普通任务和邮件引入业务幂等键。共享 `trading_runtime` 也应与执行作用域对齐，避免不同部署互相覆盖意愿。

### 6.8 P1：保存成功与业务生效的反馈不够精确

**当前证据：**数据库成功、文件失败时整体接口报错，但数据库不会回滚；数据库写失败后只探测目标专属键，可能漏掉实际读取链中的旧全局键。保存响应没有来源、版本和“交易循环已应用”的确认；前端自定义成功提示还可能覆盖降级消息。[S3][S15]

**建议：**明确返回 `account / revision / persisted_to_db / mirror_status / warning`；提供交易循环的 `applied_revision`。数据库不可用时不把“探测结果为空”视作明确可降级证明。区分缺记录、损坏、超时、权限失败，制定可解释的恢复与冲突处理流程。镜像更新可异步重试，但不能掩盖主存结果。

### 6.9 P1：参数校验、配置生效边界与账户管理仍需统一

**当前证据：**已有周期、杠杆、数量、BOLL、止盈止损等校验，但保存接口未统一校验顶层与所有嵌套对象类型，执行间隔和部分总开关也缺严格类型 / 范围约束。配置读回后没有统一 schema 验证；文件或直接改库可绕过保存校验。[S3][S7]

**建议：**建立带 `schema_version` 的配置模型，集中校验结构、有限数值、布尔值、周期组合、范围和账号；读取降级数据也校验。建立字段生效清单，区分“每轮读取、初始化读取、需要重建客户端”。例如邮件冷却已有显式热同步，通知器初始化读取文件的其他行为不能据此推定都已热更新。

用户操作文案应明确区分“停止新增交易、保留仓位保护、暂停策略、停止线程、撤单、平仓”，减少把一个开关当作全部资金保护的误解。

### 6.10 P2：扩展瓶颈主要是共享计算通道与调度可观测性

**当前证据：**策略引擎使用模块级参数，已有进程级 `PRO3_LOCK`，因此不能简单靠增加线程数成倍提速；长批量分析与实盘可能争抢同一计算通道。APScheduler 任务列表以注册信息为主，没有统一的任务执行流水。[S2][S11][S12]

**建议：**

- 先测量每轮耗时、锁等待、行情请求、数据库读次数、错过触发和连续失败，再决定优化点。
- 逐步把策略计算改成显式参数与返回值，减少模块全局状态；确需并行时使用隔离计算进程，不直接绕过锁。
- 交易执行优先，批量分析与摘要任务降优先级；普通后台重任务可使用独立执行器。
- 统一记录 job ID、计划触发时间、实际开始 / 结束、执行实例、账号、配置版本、结果及错误。
- 显式约定调度时区，并统一夜间窗口与 cron 时刻；当前触发器构造未统一显式指定业务时区，不应假定任何部署都按北京时间执行。
- 将核心交易配置接口逐步从大型 `app.py` 拆到蓝图与服务层，前端脚本从大型模板拆出，降低配置逻辑分散和回归成本。

### 第一阶段：先补资金与账号安全边界

- 修复配置编辑会话的账号绑定与乱序响应。
- 消除实盘中的跨账号文件 / 全局隐式回退。
- 修复批量账户操作使用共享文件确定目标的路径。

验收：A / B 账号交错加载和保存不串写；任何来源不明的配置不能驱动新增风险；等待恢复时取消后绝不再启动；数据库故障不把停止意愿伪装成已持久化。

### 第二阶段：形成可核对的配置与调度状态闭环

- 引入配置版本、冲突检测、每轮快照和已应用版本。

- 修复 shutdown 后复用调度器；精准重注册指定任务。
- 按账号保存原子镜像，返回主存 / 镜像的独立结果。

验收：并发修改不丢字段；库 / 文件错误组合均有准确反馈；任务关闭后的在途行为可解释；停止再恢复后能观察到实际测试任务执行，而不只是状态灯变绿。

### 第三阶段：为多实例和规模增长做准备

- 明确 Web 与执行角色，增加账号级执行租约及防旧主机制。
- 建立任务执行流水、幂等键和统一时区。
- 根据基准数据调整计算隔离、优先级、缓存与执行器。

验收：两个进程竞争同一账号时仅一个取得执行权；长分析不会无界拖延关键风险管理；停机、恢复、错过触发都有可追踪记录。

| 测试主题 | 必测组合 |

| 配置存储 | DB 成功 / 文件失败；DB 写失败但读成功；专属键缺失但全局键存在；DB 不可用后恢复 |

## 九、最终判断

当前实现的核心思路是合理且清晰的：用轻量进程内调度承载后台工作，用独立顺序循环管理实盘，用数据库统一配置来源，用账号键区分策略，用多道锁与对账保护交易执行。

下一步的重点不是单纯增加任务数量或线程数量，而是让四件事能够被明确回答：**现在为哪个账号执行、用的是哪一版配置、停止指令是否真正生效、失败或重启后由谁取得执行权。**

把账号隔离、配置版本、生命周期与状态协调补齐后，这套结构才能从“单实例可管理”进一步演进到“异常情况下仍可验证、可解释、可扩展”。
