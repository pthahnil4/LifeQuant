# 每日评级总控台（原"每日多维打卡"）设计文档

> 状态：已实施（批次15）；2026-09-26 增补：改名 + 日记双向关联 + 23:30 收尾提醒
> 日期：2026-09-26
> 涉及模块：监控台首页 / 热量缺口 / 交易(OKX) / 任务计划(学习) / 日记本 / checkin 模块

---

## 1. 背景与目标

在总控台增加"每日多维打卡"：一天一条记录，自动收集三大项数据并判定达标，
再由本人补充自我评级与文字评价。

| 维度 | 目标 | 数据来源 | 采集方式 |
|------|------|----------|----------|
| 减肥（热量） | 当日热量缺口 ≥ 800 kcal | `calorie_records` 表 | 本地 DB 只读 |
| 交易 | 当日盈利 ≥ 8% | OKX 账户权益 + 本地 `balance_history` 快照 | 自动拉取 OKX（只读） |
| 学习 | 时长 ≥ 10 小时 且 完成任务 ≥ 2 个 | `plan_slots`（duration_minutes）+ 任务树（task_links） | 本地 DB 只读聚合 |
| 自我评级 | E ~ S 六档，可选 | 用户手选 | 手动 |
| 评价 | 纯文本 | 用户输入 | 手动 |

设计原则：
- **自动项只读采集，不反向写任何业务表**（不碰 calorie / plan / balance 的写路径）。
- **打卡落库即定格**：提交时把三项自动指标的当时数值快照进打卡记录，之后源数据再变
  （如补录热量、补打卡学习格）不回改历史打卡；当天未提交前反复打开页面都取最新值，
  当天内可重复提交（upsert 覆盖）。
- 复用现有基础设施：OKX 只读限频出口 `_rl_call`、账号解析 `_resolve_task_account`、
  kv_store 配置、余额快照 `balance_history`。

## 2. 现状调研结论（数据通路盘点）

### 2.1 热量缺口（已有，直接读）
- 表 `calorie_records`，主键 id = 日期（YYYY-MM-DD），字段 `calorie_deficit`
  即当日热量缺口（摄入缺口 + 运动消耗），由 `CalorieCalculator` 在保存时算好。
- 判定：`SELECT calorie_deficit FROM calorie_records WHERE id = 今日`；
  无记录 = 未录入（状态"缺数据"，不等于不达标，UI 区分显示）。

### 2.2 交易盈利（无每日金额记录，需新建采集）
现状：
- `GET /plan/api/account-balance` 已实现后端代理 OKX `/api/v5/account/balance`
  取 `totalEq`（USDT 总权益），且每次查询后自动追加 `balance_history` 快照
  （account_key + ts毫秒 + balance，Double 精度）。
- `api_routes.py` 已有 `get_account_bills`（OKX 近 7 日账单流水）封装与
  `_rl_call` 统一限频/退避出口；`_BILL_TYPE_MAP` 中 type=2 为交易、1 为划转等。
- 账号口径：`_resolve_task_account()`（运行中调度器账号 → DEFAULT_ACCOUNT 兜底）。

**日收益率算法（主口径：权益差分法）**
```
base  = 昨日最后一个 balance_history 快照（本地）
live  = 实时 OKX totalEq（经 _rl_call 限频）
raw_pct   = (live - base) / base × 100
```
**入金/出金失真修正（辅助口径：账单流水法）**
- 权益差分会把充值/划转误算成盈利。拉取 OKX bills（type ∈ 划转/交易等资金移动类），
  将当日净入金 net_transfer 从差额中剔除：
```
adj_pct = (live - base - net_transfer) / base × 100
```
- bills 仅支持近 7 日（更早需 bills-archive，本期不做）；bills 拉取失败时
  降级用 raw_pct 并在 UI 标注"未剔除资金进出"。

**基准缺失的处理（冷启动）**
- 昨日无快照：依次回退 ①最近一个历史快照（标注基准日期）②当日首个快照
  ③都无 → 状态"缺数据"，引导用户点一次"刷新余额"积累快照。
- 打卡提交时把 base / live / net_transfer / pct 一并定格进记录。

**限频与缓存策略**
- 页面自动加载**不打 OKX**：优先读当日 checkin 缓存快照（新表字段），
  缓存超过 TTL（默认 5 分钟）才允许刷新，且刷新只由用户点"⟳ 刷新交易数据"
  或提交打卡时触发 → 与现有只读限频纪律一致（问题#8 口径）。
- 可选增强（本期不实现，留接口）：复用现有定时任务体系每日 23:50 自动抓一次
  收盘权益写快照，保证 base 永远不缺。

### 2.3 学习时长与任务完成数（已有，需新增聚合查询）
- 时长：`plan_slots.duration_minutes`，`filled_at` 前缀匹配当日。
  现有 `_calc_slot_hours_by_date` 逻辑一致，但它走整树读取；本模块在
  `plan_repo` 新增**窄聚合 SQL**（JOIN plan_cards，按 filled_at LIKE '今日%'
  SUM(duration_minutes)），避免 200卡×100格 全量拉取的已知性能坑。
- 任务完成数：打卡时 `task_links: [{task_id, state: doing|done}]` 写进格子记录。
  口径 = 当日所有已打卡格子 record.task_links 中 state='done' 的 **去重 task_id 数**
  （同一任务被多条打卡关联只算 1 个）。
- 只统计学习任务卡（type='learn'）还是学习+交易卡都算？
  **默认口径：只算 learn 卡**（"学习满10小时且完成两项任务"语义），阈值配置里留开关。

### 2.4 评级与评价（纯新增）
- 评级：固定六档 `E / D / C / B / A / S`，可选（允许当天不评）。
  本期不做加权分，纯记录；表里同时存 `all_passed` 布尔（三项全达标）方便日后统计。
- 评价：纯文本，长度上限 2000 字符。

## 3. 总体设计

### 3.1 页面入口（两处）
1. **新页面 `/checkin`「每日打卡」**：完整交互（三块指标卡 + 刷新 + 评级 + 评价 +

   DEFAULT_ITEMS + ACTIVE_PAGE_ALIASES + CATALOG 同步登记）。

   评级 + "去打卡"链接。首页只读展示，不做提交交互，保持监控台轻量。

### 3.3 数据表 `daily_checkins`
```
date            VARCHAR(10)  PK          -- YYYY-MM-DD（本地日）
-- 热量项
cal_value       FLOAT NULL               -- 当日 calorie_deficit 定格
cal_passed      TINYINT(1) DEFAULT 0
cal_status      VARCHAR(16)              -- ok / no_data
-- 交易项
trade_base      DOUBLE NULL              -- 基准权益（昨日最后快照）
trade_base_date VARCHAR(10)              -- 基准快照所属日期（回退时≠昨日）
trade_live      DOUBLE NULL              -- 提交时实时权益
trade_transfer  DOUBLE NULL              -- 当日净入金（剔除用；NULL=未取到）
trade_pct       DOUBLE NULL              -- 收益率 %（修正后口径）
trade_passed    TINYINT(1) DEFAULT 0
trade_status    VARCHAR(16)              -- ok / no_base / api_error / no_data
trade_src       VARCHAR(16)              -- live / cache
-- 学习项
learn_hours     FLOAT NULL               -- 当日学习小时数定格
task_done_count INT DEFAULT 0            -- 当日去重完成任务数
learn_passed    TINYINT(1) DEFAULT 0     -- hours≥阈值 且 tasks≥阈值
learn_status    VARCHAR(16)              -- ok / no_data
-- 手动项
rating          VARCHAR(2) NULL          -- E/D/C/B/A/S，可空
comment         TEXT                     -- 评价，纯文本
all_passed      TINYINT(1) DEFAULT 0     -- 三项全达标（提交时计算定格）
account_key     VARCHAR(32)              -- 交易项取数账号（审计用）
created_at / updated_at DATETIME
```
配套缓存表 `trading_daily_snapshots`（可选合并为 kv_store，推荐独立表便于按日查询）：
```
account_key VARCHAR(32)  PK1
date        VARCHAR(10)  PK2
base_balance   DOUBLE NULL   -- 当日解析出的基准
live_balance   DOUBLE NULL   -- 最近一次实时权益
net_transfer   DOUBLE NULL
pct            DOUBLE NULL
fetched_at     VARCHAR(19)   -- 最近拉取时间（TTL 判断）
```

### 3.4 API 设计
| 接口 | 方法 | 说明 |
|------|------|------|
| `/checkin` | GET | 页面 |
| `/checkin/api/today?date=` | GET | 聚合三项自动指标 + 已存打卡。**默认交易项读缓存不打 OKX**；返回各分项 value/passed/status/阈值 |
| `/checkin/api/refresh-trade` | POST | 手动刷新交易数据：`_rl_call(get_account_balance)` + bills 修正，写 `trading_daily_snapshots` 缓存后返回。TTL 内重复调用直接回缓存 |
| `/checkin/api/checkin` | POST | 提交/覆盖当日打卡：服务端**重新采集**三项自动值（交易项允许用 TTL 内缓存）→ 定格落库；body 只带 `rating`、`comment`、`date`（date 仅允许今天或过去，禁止未来） |
| `/checkin/api/history?start=&end=` | GET | 历史列表（首页状态条与打卡页历史共用，range ≤ 62 天，对齐 backfill-balances 口径） |

安全与纪律：
- 所有 OKX 调用仅走 `_rl_call` 限频出口，密钥不出服务端（与 account-balance 一致）。
- GET 接口一律不写业务表（缓存表写入仅发生在 POST refresh-trade / checkin）。
- 写接口挂 Web 闸门同源校验（与 navigation 写接口同口径）。
- 提交时服务端重算达标，不信任前端传来的 passed/value。

### 3.5 阈值配置（kv_store）
key = `checkin_config`（全局即可，本期不按账号）：


## 4. 交互流程

### 4.1 打开打卡页
```
GET /checkin/api/today
 ├─ 热量：查 calorie_records 今日 → 有=数值+达标灯 / 无="未录入"灰灯+跳转链接
 ├─ 学习：窄聚合 plan_slots 今日 → 小时数 + 任务完成数 + 达标灯
 └─ 交易：读 trading_daily_snapshots 缓存
      ├─ 缓存新鲜(<TTL) → 直接显示（标注"缓存于 HH:MM"）
      └─ 无/过期 → 显示"待刷新"，用户点 ⟳ 触发 refresh-trade
```

### 4.2 提交打卡
```
选评级(可跳过) + 填评价(可空) → POST /checkin/api/checkin
 服务端：重采集三项（交易用缓存或现拉一次）→ 计算 passed/all_passed → upsert
 返回定格后的完整记录，前端切换到"今日已打卡"态（可再次修改覆盖）
```

### 4.3 首页状态条
监控台 index.html 顶部（header 下方）一行三灯 + 评级徽章 + "去打卡"按钮；
数据来自 `/checkin/api/today`（缓存口径，不在首页触发 OKX 调用）。

## 5. 边界情况与开放问题（已给默认决策）

| # | 问题 | 默认决策 |
|---|------|----------|
| 1 | 交易 8% 是"当日账户总权益涨幅"还是"已实现盈亏"？ | **当日总权益涨幅（剔除净入金）**。已实现盈亏口径 OKX 需 positions-history/bills 逐仓归集，误差大、限频重，本期不做 |
| 2 | 当日出入金频繁导致账单修正不准 | UI 显示 net_transfer 数值供人工核对；明显异常时用户可在评价里备注，评级本来就是主观兜底 |
| 3 | 昨天没有余额快照（冷启动） | 回退最近快照并标注基准日；完全无快照 → "缺数据"，打卡仍可提交（trade_status=no_data，交易项不计达标） |
| 4 | 学习"完成两项任务"的口径 | 当日打卡格 task_links 中 state=done 的去重任务数；无关联任务=0 |
| 5 | 补录场景（前一天忘打卡） | POST checkin 的 date 允许过去日期，自动指标按该日历史数据重算（热量/学习可算，交易只能取该日快照差分，缺则 no_data） |
| 6 | 跨日边界 | 一律本地时区自然日；23:5x 提交按当日算 |
| 7 | 多账号 | 交易项固定 `_resolve_task_account()` 账号，account_key 落库审计；不做多账号合并 |
| 8 | 评级是否必填 | 可选（用户原话"可选"）；all_passed 与 rating 相互独立 |

## 7. 风险与不变量

- **不新增任何自动定时 OKX 调用**（可选增强须另行评审），维持只读限频纪律。
- 打卡模块对 calorie / plan / balance_history **零写入**；唯一写目标是自己的两张新表。
- MySQL 侧 DDL 与模型是两条独立口径，SQLite 冒烟全绿不能外推 MySQL 结论（既有验收边界）。
- 首页状态条懒加载失败时静默降级（不阻塞监控台主功能）。

### 8.1 名称统一

### 8.2 日记双向关联
- `daily_checkins` 新增可空列 `diary_entry_id`（三处接线：models / `_REQUIRED_COLUMNS`
  增量加列 / `db_schema.sql`）。提交打卡时定格回填当日日记条目 id。
- `GET /checkin/api/today` 增加 `diary` 子对象：`{has_entry, entry_count, entry_id}`，
  由 `_collect_diary_status` 只读 `diary_entries` 当日存在性算出（隐私条目只暴露存在性），
  优先取回指条目 `linked_from='checkin:YYYY-MM-DD'`。**GET 仍零 OKX、零写入**。
- 打卡页 → 日记本：`/diary?date=YYYY-MM-DD&link=checkin:YYYY-MM-DD`（diary.js 已支持
  `?date`/`?link`，写入条目时带 `linked_from` 回指）。日记本 → 打卡页：日记按天分组
  头部「📋 查看今日评级」链到 `/checkin?date=…`，checkin.js 支持 `?date=` 深链回看。
- 未写日记提醒：当日已打卡但 `diary.has_entry=false` → 打卡页顶部友好提示 + 一键去写日记。
- 未评级提醒：当日已打卡但 `rating` 为空 → 评级选择区高亮（`.ck-rating.need`）；
  首页状态条同步显示"待评级"徽章。

### 8.3 23:30 收尾提醒邮件
- 新增调度任务 `checkin_diary_reminder`（cron 23:30），`crypto/task/monitor/checkin_diary_reminder.py`。

- 邮件正文：三项指标摘要（读 `daily_checkins` 定格列，不重算不打 OKX）+ 缺口提示 +
  「去补评级 / 去写日记」两个直达按钮。
- 邮件复用 `MessageNotifier._dispatch_email` + `EmailTemplates._wrap_html` +
  `get_admin_email`（与既有纪律/倒计时提醒同款出口，未重复造轮子）。
- 配置 kv `checkin_diary_reminder_config {"enabled":true}`；开关/文件急停经
  `register_job` 统一守卫生效；`register_default_jobs` 与 `SWITCHABLE_JOB_LABELS` 已接线。
- **不变量复核**：本任务只读 `daily_checkins` / `diary_entries`，零写入、零 OKX —— §7
  "不新增自动定时 OKX 调用"红线仍成立。与既有 `checkin_reminder`（任务卡倒计时，
  每 5 分钟巡检计划树）是两个独立任务，勿混淆。
