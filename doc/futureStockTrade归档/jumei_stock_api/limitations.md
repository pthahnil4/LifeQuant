# 实测限制与坑（limitations）

> 全部为直连 REST 通道实测结论（`sz000001` / `sh600519` 交叉验证），非文档推测。

## 1. 三条 K线接口的根数上限并不相同（实测）

**A. `a_kline`(/stock/a/kline) 与 `hs_kline`(/stock/hs/kline)：硬顶 100 根，且只有"最近"**
- `pageSize` 传 `10 / 100 / 500 / 1000 / 2000 / 5000` → **一律只返回 100 根**（连 ps=10 也给 100）。
- `pageNo` / `page` / `offset` / `start` / `end` / `date` 等翻页或日期参数**全部无效**，窗口纹丝不动。
- 官方参数表也仅有 `symbol/type/pageSize/ma`（a）与 `code/period/fuquan/pageSize`（hs），无日期/页码。

**B. `hs_mink`(/stock/hs/mink 分钟K含均线)：★不受 100 限制★**（早前误把它也归为100封顶，已纠正）
- 干净状态实测单次足额返回：`1000→1100→1200→1500→1800` 根均可，`60分钟` 拉满 ≈ **22 个月**（2024-11 ~ 2026-09）。
- `pageSize≥2000` 触发业务 `code=502`「网络不稳定」（请求过重的保护，非翻页）。
- ⚠️ **专属限流坑**：连续高频大 pageSize 打 mink 后，该接口会对**任意大小（哪怕 ps=20）都返回 `code=200` 但 candle 为空**；
  此时 `hs_kline`/`a_price` 仍正常 → 说明是 **mink 单接口限流**，非全账号。需**冷却数分钟**恢复。
  → 批量回补务必**控频 + 失败退避重试**，勿并发猛打。

## 2. 根数上限对应的时间覆盖

| 接口/周期 | 单次上限 | 覆盖 | 说明 |
|------|-----------|------|------|
| hs_mink 60分钟 | ≈1800 根 | **≈ 22 个月** | 一次即可回补近 2 年 1H |
| hs_mink 120分钟 | ≈1000+ 根 | 数年 | 周期越长覆盖越久 |
| hs_mink 5分钟 | ≈1800 根 | ≈ 1.5 个月 | 1m 更短 |
| a_kline/hs_kline 60分钟 | 100 根 | ≈ 1 个月 | 远不如 mink |
| a_kline/hs_kline 日K | 100 根 | ≈ 5 个月 | |

> 结论：**想要较长的 1H 历史，首选 `hs_mink`（单次可回补近 2 年），而非 a_kline/hs_kline。**
> 但三者都只到「当前」、无历史翻页 —— 更早于窗口的历史仍须定时采集入库。

## 3. 对建库/采集的影响（核心决策依据）

- **1H 近 2 年可用 `hs_mink` 一次性回补**（控频拉取），比原判断乐观得多。
- **要 2 年之前 / 全量长历史 → 仍需自建"定时抓取 → 落 TDengine"采集器**，靠轮询把滚动窗口逐段固化。
- **1H 日常增量：每天收盘后跑一次即可**，窗口重叠冗余大，`ts` upsert 去重，绝不断档。
- **1m**：mink 单次约 1800 根 ≈ 1.5 个月，日频采集可无损累积（比 a_kline/hs_kline 强）。
- 采集器必须内置**退避重试 + 失败本地队列 + 限流冷却**：mink 高频会被限流返回空、≥2000 会 502。

## 4. 其它注意

- 数值字段多为 **String**，入库前统一转数值（参考 `kline/providers/base.py` 的 `to_standard_ohlcv`）。
- 时间：`day` 为北京时间墙钟；`candle` 为 Unix 秒。入库前固定统一到一套口径（建议 UTC 毫秒），
  与前端 `chart_serialize` 的 naive-墙钟约定对齐，避免时区错位。
- 复权：`/stock/hs/kline` 支持 `fuquan`（0/1/2）；`/stock/a/kline` 未见复权参数，口径待确认。
- MCP 数据面在某段时间整体 502，落地**一律走直连 REST**。
